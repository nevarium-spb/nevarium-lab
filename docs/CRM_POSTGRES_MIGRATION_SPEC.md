# ТЗ: переписать CRM (`G:\nevarium-crm`) с SQLite на PostgreSQL

Это Этап 3 из [POSTGRES_MIGRATION_PLAN.md](./POSTGRES_MIGRATION_PLAN.md) — детально,
для сессии, которая будет делать саму работу в репозитории CRM.

Работа делается **до подключения к реальной базе**: этап 2 плана переезда (создание
базы данных на Timeweb) уже пройден, `DATABASE_URL` у владелицы на руках. Она
понадобится только на этапе 4 (запуск CRM), не раньше — вся работа этого документа
делается локально.

---

## Зачем

`App Platform` не сохраняет файлы контейнера между деплоями (документация Timeweb:
«каждый новый деплой запускает новый Docker-контейнер, в котором не сохраняются
данные из предыдущих версий»). CRM сейчас хранит все данные в файле SQLite —
значит любой деплой стирал бы все заявки. Нужна база, которая живёт отдельно от
приложения. Делаем это сейчас, потому что в CRM пока **ноль пользователей и ноль
заявок** — ломать нечего, дешевле момента не будет.

---

## Что там на самом деле — проверено по коду, не на глаз

Более ранняя оценка «около 450 мест в коде» была завышена — это была прикидка по
грубому поиску, который цеплял и посторонние вызовы (`Map.get()` в лимитере
логина и подобное). Реальные цифры, посчитанные точным поиском по `db.<метод>(`:

| Файл | Обращений к базе |
|---|---|
| `server/app.js` | 91 |
| `server/telegram.js` | 5 |
| `server/bootstrap.js` | 2 |
| `server/backup.js` | 1 |
| `server/seed-admin.js` | 1 |
| **Итого в продакшен-коде** | **100** |
| `server/api.test.js` (тесты) | 97 |

Из них **7 мест** используют `db.transaction(() => {...})()` — синхронный API
`better-sqlite3` для атомарных операций (например, создание серии задач воронки
возврата — вставка в `winback_sequences` и несколько строк в `tasks` одной
транзакцией).

### Схема

10 таблиц: `users`, `contacts`, `deals`, `tasks`, `interactions`, `outbox`,
`projects`, `winback_sequences`, `pd_requests`, `audit_log`. 8 миграций с
реальной историей решений — мультипроектность (`project_id`, CORS-`origins`
по проекту), воронка возврата, исполнение прав субъекта ПДн (152-ФЗ), журнал
аудита.

### Стек

Fastify 5, `better-sqlite3` (WAL-режим, `foreign_keys=ON`), `bcryptjs`, тот же
процесс отдаёт и API, и собранный React-фронт (`@fastify/static`). Тесты —
`vitest`, поднимают SQLite **в памяти** (`:memory:`) в `beforeEach` — быстро,
изолированно, без внешних зависимостей.

---

## Решения, принятые заранее — чтобы сессия не тормозила на развилках

### 1. Библиотека — `pg` (node-postgres), не ORM

Не Prisma и не Drizzle. Весь текущий код — это параметризованные «сырые» SQL-запросы
через `.prepare().get()/.all()/.run()`. Схема стабильна, сложных join'ов нет — ORM
здесь добавил бы объём переписывания ради выгоды, которая не нужна для CRM такого
размера.

### 2. Совместимый слой поверх `pg` — минимизирует правки самого SQL

Написать модуль-адаптер (`server/db-adapter.js` или подобное), который поверх `pg.Pool`
даёт интерфейс, похожий на нынешний `better-sqlite3`, но асинхронный:

```js
const stmt = db.prepare(sql)      // как раньше
await stmt.get(...params)         // вместо .get() — возвращает одну строку
await stmt.all(...params)         // вместо .all() — возвращает массив
await stmt.run(...params)         // вместо .run() — { changes, lastInsertRowid }
```

Внутри адаптер сам переводит `?`-плейсхолдеры SQLite в `$1, $2, ...` для Postgres
(простая, безопасная замена — сами тексты запросов не пользовательский ввод, они
захардкожены в коде). Это значит: **текст большинства SQL-запросов можно оставить
почти как есть**, меняется в основном то, что каждый вызов теперь надо `await`-ить.

### 3. Схема — не переносить 8 миграций по шагам, а написать одну чистую

Раз переносить нечего (данных нет), не нужно механически повторять историю из
8 миграций SQLite, включая обходы её ограничений (например, `project_id` в v3
специально без `REFERENCES` — это была обходка конкретно под SQLite, в Postgres
такого ограничения нет вообще). Пишем **один SQL-файл** с итоговой схемой в её
нынешнем виде (эквивалент всех восьми миграций сразу), нормальным Postgres-синтаксисом,
со всеми внешними ключами там, где они осмысленны логически, а не там, где раньше
мешал SQLite.

---

## Таблица замен: SQLite → PostgreSQL

| В коде сейчас | Стало | Комментарий |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | стандартная замена |
| `INTEGER` как булево (0/1: `archived`, `done`, `demo`, `suspicious`) | оставить `INTEGER` 0/1 | сознательно НЕ переводить в `BOOLEAN` — тогда не придётся трогать сравнения вида `archived = 0` по всему коду. Отдельная, необязательная работа на будущее |
| `strftime('%Y-%m-%dT%H:%M:%fZ','now')` (в миграции v3, дефолтные значения `projects`) | обычная ISO-строка из JS (`now()` уже есть в `db.js`, используется везде остальным кодом) | при пересборке схемы с нуля этот SQLite-специфичный вызов просто не нужен |
| `.lastInsertRowid` | `INSERT ... RETURNING id`, читать `id` из результата | |
| `.changes` | `rowCount` из результата запроса | |
| `db.transaction(() => {...})()` (синхронный) | асинхронный хелпер `withTransaction(pool, async (client) => {...})`: `BEGIN` → операции → `COMMIT`/`ROLLBACK` в `try/catch`, клиент возвращается в пул в `finally` | нужно написать один раз, использовать в тех же 7 местах |
| `CREATE INDEX ... WHERE sent_at IS NULL` (частичный индекс) | без изменений | синтаксис идентичен в Postgres |
| `PRAGMA journal_mode/busy_timeout/foreign_keys/user_version` | убрать | WAL — поведение Postgres по умолчанию; внешние ключи всегда включены (нельзя отключить, как в SQLite); `busy_timeout` при необходимости — `statement_timeout` на уровне пула; `user_version` не нужен, раз миграции сведены в одну схему |

## Тесты — отдельная развилка, тоже решаем заранее

`:memory:` SQLite в `beforeEach` — самое SQLite-специфичное место во всём проекте,
прямого аналога в Postgres нет.

**Решение: `pg-mem`** — чистый JS-мок Postgres в памяти. Ближе всего по духу к
нынешнему подходу: быстро, ноль внешних зависимостей, каждый тест поднимает
свежую базу так же, как сейчас. Не идеально повторяет поведение настоящего
Postgres в редких углах SQL — поэтому:

- [ ] Перед первым продакшен-деплоем — **один ручной прогон** всего набора тестов
      против настоящей managed-базы (той, что уже создана на Timeweb, на тестовых
      данных, не боевых), чтобы поймать расхождения `pg-mem` vs реальный Postgres,
      если они есть.

## Порядок работы по сессиям

1. **Фундамент.** Новый `schema.sql`, адаптер `db-adapter.js`, замена
   `better-sqlite3` → `pg` в `package.json`. Без переноса логики — просто база
   под остальную работу.
2. **`server/db.js`** (миграции/дамп/бэкап-хелперы) на новый адаптер — самый
   маленький файл из тех, что трогают базу, хорошая проверка подхода на малом
   масштабе перед большим.
3. **`server/app.js`** (91 обращение, основной объём) — по разделам: контакты →
   сделки → задачи → взаимодействия → outbox → projects → воронка возврата →
   запросы по ПДн / журнал аудита. Не пытаться одним заходом — резать по разделам,
   после каждого гонять относящиеся к нему тесты.
4. **Остальное**: `telegram.js`, `backup.js`, `bootstrap.js`, `seed-admin.js`
   (9 обращений на четверых).
5. **Тесты** (`api.test.js`, 97 обращений + `beforeEach`) — перевести на `pg-mem`.
6. **Прогнать весь набор**, поправить расхождения.
7. **Ручная проверка** — поднять локально с реальным `DATABASE_URL` от Timeweb
   (тестовые данные, не боевые), пройти сценарий руками: логин → создать контакт
   → сделку → задачу → отметить сделку «Проиграно» (должна завестись воронка
   возврата) → экспорт JSON → импорт JSON → запрос по ПДн → проверить журнал
   аудита.

## Сознательно не входит в эту работу

- **Никаких изменений в API-контракте.** Сайты (`nevarium-lab.ru`,
  `nevarium-vizor.ru`) не должны почувствовать разницу — те же адреса, те же
  форматы ответов.
- **Никаких изменений в бизнес-логике или поведении** — только смена базы под
  капотом.
- **Фронтенд CRM (React) не трогается вообще** — он говорит с API по HTTP, ему
  всё равно, что за базой на сервере.
- **Архитектурный шлюз** (чтобы браузер не бил в CRM напрямую) — отдельная
  задача из ТЗ Визора, не часть этой работы.
- **Перевод `INTEGER`-булевых полей в настоящий `BOOLEAN`** — можно сделать
  потом отдельно, не блокирует переезд.
