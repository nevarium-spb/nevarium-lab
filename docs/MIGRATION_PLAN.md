# План миграции на Astro

Документ-план. Код по нему пока не писался. Читать сверху вниз.

## 1. Зачем это вообще

Сейчас сайт — SPA (single page application): весь сайт это **один** HTML-файл, а страницы
рисует JavaScript уже в браузере. Из-за этого:

- **Соцсети и мессенджеры видят одинаковое превью для всех страниц.** Ссылка на тарифы и
  ссылка на политику выглядят в Max/Telegram одинаково, потому что превью берётся из
  единственного `index.html`, а `usePageMeta` меняет заголовок уже после запуска JS —
  краулер этого не дожидается.
- **Поисковики индексируют сайт хуже**, потому что вынуждены выполнять JS, чтобы увидеть текст.
- **Нет отдельных HTML-страниц** — нельзя дать canonical-ссылку, свой `og:image` на каждую
  страницу, нормальный sitemap.
- **Если JS не загрузился — сайт пустой.** Не «поломанный», а буквально белый экран.

Миграция превращает каждую страницу в настоящий HTML-файл, который отдаётся готовым.
Это единственная причина мигрировать. Дизайн, тексты и поведение не меняются.

**Чего миграция НЕ даст:** сайт не станет заметно быстрее для человека (он и так быстрый),
не решит вопросы безопасности CRM, не заменит реальные кейсы на сайте.

## 2. Выбор: Astro, не Next.js

**Рекомендация — Astro.** Причины, по порядку важности:

1. **Сайт на 95% состоит из статичного текста.** Astro по умолчанию отдаёт HTML вообще без
   JavaScript, а JS подключает только там, где он реально нужен («острова»). Из 8 страниц
   интерактивны буквально 9 кусочков — это ровно та модель, под которую Astro сделан.
2. **Существующие React-компоненты переносятся как есть.** Чат-бот, формы, canvas-фон,
   переключатель темы не надо переписывать — Astro умеет встраивать готовые React-компоненты
   через `@astrojs/react`. Это резко снижает риск сломать работающее.
3. **Меньше новых понятий.** В Next.js (App Router) пришлось бы разбираться с серверными и
   клиентскими компонентами, директивой `'use client'` и правилами их сочетания. Для проекта,
   который поддерживает не программист, это лишняя сложность на годы вперёд.
4. **Файловая маршрутизация 1:1.** Восемь страниц становятся восемью файлами. Нет `App.tsx`
   со списком роутов — структура папок и есть структура сайта.
5. **Vercel поддерживает Astro «из коробки»** — схема деплоя (push в GitHub → автосборка)
   не меняется вообще.

**Когда стоило бы выбрать Next.js:** если бы появился личный кабинет, авторизация, база
статей с админкой или серверная логика. Ничего этого не планируется — Next был бы избыточен.

**Более дешёвая альтернатива, если миграцию не хочется вообще:** подключить к текущему Vite
плагин пререндера (`vite-plugin-ssg` и подобные). Он сгенерирует HTML для каждой страницы и
закроет 70% SEO-проблем без смены фреймворка. Минус — решение более хрупкое и хуже
документированное, а структура кода останется прежней. Если цель «просто чтобы превью в
соцсетях были разные» — этот путь короче в разы, и его стоит рассмотреть всерьёз.

## 3. Что НЕ трогаем во время миграции (жёсткие рамки)

Это самое важное правило всего плана. Миграция — это **перенос**, а не улучшение.

- ❌ **Не трогаем `global.css`.** Все 2050 строк переезжают одним файлом, как есть. Разбор
  CSS на модули — отдельная задача **после** миграции. Две большие перестройки одновременно
  = невозможно понять, что именно сломалось.
- ❌ **Не трогаем тексты.** Ни одной формулировки. Тексты построены по продуманной стратегии
  (см. HANDOFF.md, раздел «Логика текстов») и подтверждались владелицей отдельно.
- ❌ **Не трогаем дизайн и вёрстку.** Цель — чтобы после миграции скриншоты «до» и «после»
  совпадали попиксельно.
- ❌ **Не трогаем логику отправки в CRM** (`src/lib/leads.ts`). Она уже проверена и работает
  корректно, включая честную ошибку при недоступной CRM.
- ❌ **Не убираем inline-стили из JSX** — это тоже задача «после».

Единственное исключение — `Reveal` и `Stat` (см. фазу 3): их замена на маленькие обычные
скрипты не косметика, а прямое следствие отказа от React на статичных страницах.

## 4. Карта текущего кода

Что выяснено при разборе — от этого зависят все фазы.

**Хорошие новости:**
- Динамических роутов нет (`/услуга/:id` и подобного) — все 8 страниц статичны
- Данных с сервера при отрисовке страницы не запрашивается
- Контент уже вынесен в `src/data/` — переносится без изменений

**Статично (JavaScript не нужен вообще):**

| Файл | Что это |
|---|---|
| `data/content.tsx` | услуги, кейсы, тарифы, FAQ, шаги |
| `data/icons.tsx` | SVG-иконки |
| `components/Footer.tsx` | подвал |
| `components/Logo.tsx` | логотип |
| `components/SectionHead.tsx` | заголовок секции |
| `components/CTABand.tsx` | блок призыва |
| `components/HeroPanel.tsx` | дашборд-панель в первом экране |
| тексты всех 8 страниц | ~1100 строк разметки |

**Интерактивно (нужен JavaScript — станет «островом»):**

| Компонент | Что делает | Как переносим |
|---|---|---|
| `Header.tsx` | реакция на скролл, мобильное меню | React-остров, `client:load` |
| `theme.tsx` + `ThemeToggle.tsx` | переключение тёмной/светлой темы | React-остров, `client:load` |
| `LiveBackground.tsx` | canvas-созвездие | React-остров, `client:idle` |
| `Chatbot.tsx` | чат-бот «Нева» целиком | React-остров, `client:idle` |
| `Contact.tsx` (форма) | форма заявки | React-остров, `client:visible` |
| `PdRequestForm.tsx` | запрос по перс. данным | React-остров, `client:visible` |
| `Pricing.tsx` (FAQ) | аккордеон вопросов | React-остров, `client:visible` |
| `Reveal.tsx` | появление блоков при скролле — **использован ~54 раза** | ⚠️ заменить на обычный скрипт |
| `Stat.tsx` | анимация счётчиков цифр | ⚠️ заменить на обычный скрипт |

**Ключевое решение — про `Reveal`.** Он оборачивает почти весь контент сайта. Если оставить
его React-компонентом, то весь обёрнутый текст потянет за собой React — и смысл миграции
пропадёт. Но по сути `Reveal` делает одну вещь: добавляет CSS-класс, когда блок появляется
на экране. Это заменяется **одним** маленьким скриптом на весь сайт (~10 строк), который
находит все элементы с классом `.reveal` и следит за ними. CSS-анимации при этом не меняются
вообще.

То же с `Stat` — счётчик цифр становится скриптом, читающим значение из атрибута.

**Результат такого решения:** страницы «Главная», «Услуги», «Кейсы», «Лаборатория» и
«Политика» после миграции не грузят React вообще. React останется только в общей оболочке
(шапка, тема, фон, чат) и на двух страницах с формами.

## 5. Фазы

Каждая фаза заканчивается проверяемым результатом. После каждой можно остановиться, не
оставив проект в сломанном состоянии.

### Фаза 0. Подготовка

1. Разобраться с 5 незапушенными коммитами: миграцию начинать от чистой, согласованной
   точки. Либо запушить их (когда CRM будет готова), либо явно решить, что миграционная
   ветка растёт от текущего HEAD.
2. Создать отдельную ветку под миграцию. **Старый сайт всё это время остаётся рабочим и
   задеплоенным** — прод не трогаем до самого конца.
3. Сделать эталонные скриншоты всех 8 страниц: тёмная тема, светлая тема, мобильная версия.
   Это 24 скриншота — по ним потом сверяем результат. Без этого «совпадает ли вёрстка»
   превращается в спор по памяти.

**Проверка:** ветка создана, скриншоты сохранены, прод работает как раньше.

### Фаза 1. Каркас Astro

1. Создать проект Astro внутри ветки, подключить `@astrojs/react` (чтобы React-компоненты
   работали) и `@astrojs/sitemap`.
2. Перенести без изменений: `public/` целиком (логотипы, favicon, 5 файлов шрифтов),
   `src/styles/global.css`, `src/data/`, `src/lib/leads.ts`.
3. Собрать **одну** страницу для проверки — `/privacy`. Она удобна тем, что почти целиком
   статичный текст, но содержит и форму (проверим оба режима позже).

**Проверка:** страница политики открывается локально, шрифты и стили на месте, выглядит
идентично эталонному скриншоту.

### Фаза 2. Оболочка сайта

Самая рискованная фаза — здесь живёт тема оформления.

1. Создать общий макет (аналог `Layout.tsx`): skip-link, шапка, `<main>`, подвал, фон, чат.
2. **Перенести inline-скрипт темы из `index.html` в `<head>` макета — дословно.** Он
   выставляет `data-theme` до первой отрисовки и не даёт экрану мигнуть белым при загрузке
   в тёмной теме. Это единственная причина, по которой он вообще существует, — потерять его
   легко, а заметить потерю трудно.
3. `Header`, `ThemeToggle`, `LiveBackground`, `Chatbot` подключить как React-острова.
4. `Footer`, `Logo` перевести в статичную разметку (`<Link>` → обычный `<a>`).
5. Заменить `Reveal` на общий скрипт в макете; в разметке остаётся `class="reveal"`.

**Проверка:** переключение темы работает и запоминается; при перезагрузке в тёмной теме нет
белой вспышки; фон-созвездие рисуется и реагирует на курсор; чат открывается; мобильное меню
открывается и закрывается.

### Фаза 3. Статичные страницы

Переносим по одной, в порядке возрастания сложности: Кейсы → Услуги → Лаборатория →
Политика → Главная.

- Разметка переносится почти дословно: JSX и синтаксис Astro очень похожи.
- `content.tsx` используется как есть. Нюанс: иконки в нём лежат как JSX (`icon: <IconBot />`),
  поэтому карточки с иконками пока рендерятся через React на этапе сборки — на итоговый
  HTML это не влияет, JS в браузер не уходит. Переводить иконки в чистый Astro — необязательная
  задача на потом.
- На Главной заодно заменить `Stat` на скрипт-счётчик.

**Проверка после каждой страницы:** сверка со скриншотом в трёх режимах (тёмная, светлая,
мобильная). В инструментах разработчика — убедиться, что на этих страницах React в браузер
не грузится.

### Фаза 4. Страницы с формами

1. `/contact` — форма как остров, обязательно проверить, что заявка уходит в CRM и что при
   недоступной CRM показывается честная ошибка со ссылкой на Max (не экран успеха).
2. `/pricing` — аккордеон FAQ как остров.
3. `/privacy` — форма запроса по перс. данным как остров, та же проверка на честную ошибку.
4. `/404` — страница не найдена.

**Проверка:** все формы отправляются; поведение при недоступной CRM не изменилось;
`maxLength` на полях сохранился.

### Фаза 5. Ради чего всё затевалось — SEO

Только на этом шаге появляется реальная выгода.

1. Свои `<title>` и `description` в HTML каждой страницы (не через JS).
2. `canonical` на каждой странице.
3. `og:url`, `og:image`, `og:title`, `og:description` — свои для каждой страницы. Нужна
   картинка-превью 1200×630; если её нет, сделать хотя бы одну общую с логотипом.
4. Twitter Card.
5. `sitemap.xml` — генерируется автоматически.
6. `robots.txt`.
7. JSON-LD: Organization + Service — чтобы поисковики понимали, что это за компания.
8. `noindex` на странице 404.
9. Заодно починить мелочь из аудита: ссылка на политику в тексте чат-бота сейчас просто
   текст, а не кликабельная ссылка (`src/data/bot.ts`).

**Проверка:** открыть исходный код страницы в браузере (Ctrl+U) и увидеть заголовок и
описание прямо в HTML; проверить превью ссылок через отладчик соцсетей.

### Фаза 6. Сверка и переключение прода

1. Пройти все 8 маршрутов, сверить с 24 эталонными скриншотами.
2. Отдельно проверить прямой заход и обновление страницы на каждом URL (то, ради чего
   в текущей версии добавляли SPA-rewrite; в Astro это работает само собой).
3. Задеплоить ветку на Vercel как preview — Vercel даст временную ссылку, прод при этом
   не затрагивается.
4. Сравнить preview и прод бок о бок.
5. Только после этого — слить в `main`.

**Проверка:** preview-ссылка неотличима от прода, кроме исходного HTML.

### Фаза 7. Уборка

1. Удалить `react-router-dom`, `App.tsx`, `main.tsx`, `usePageMeta.ts`, старый `index.html`.
2. Убрать SPA-rewrite из `vercel.json` — он больше не нужен (страницы настоящие). **Заголовки
   безопасности при этом оставить.**
3. Обновить `README.md`, `HANDOFF.md`.
4. `docs/DESIGN_DOC.md` уже разошёлся с кодом (описывает шрифты Unbounded/Manrope и компонент
   `useReveal`, которых нет) — либо привести в порядок, либо сократить до реально
   поддерживаемых решений.

## 6. Риски и подводные камни

| Риск | Почему опасен | Что делать |
|---|---|---|
| **Мигание белым при загрузке** | inline-скрипт темы легко потерять при переносе; заметно только в тёмной теме при холодной загрузке | перенести дословно, проверить в фазе 2 отдельным пунктом |
| **`Reveal` тянет React на все страницы** | если оставить как React-компонент, миграция теряет смысл | заменить на общий скрипт (фаза 2) |
| **Соблазн «заодно» причесать CSS** | две перестройки сразу — невозможно найти причину поломки | `global.css` переносится байт в байт; рефакторинг — отдельной задачей после |
| **CRM ещё не задеплоена** | формы при тестировании будут показывать ошибку | это ожидаемое поведение, не баг; проверять именно что показывается честная ошибка, а не экран успеха |
| **Потеря мелочей доступности** | skip-link, `aria-label`, `focus-visible` легко не заметить | сверять по списку из фазы 6, а не «на глаз» |
| **Кириллица в Poppins** | у шрифта нет кириллического набора — заголовки на русском рисуются запасным шрифтом | это было и до миграции, не «регрессия»; не пытаться «чинить» |

## 7. Как откатиться

На любом этапе до фазы 6: прод работает со старого кода, миграция живёт в отдельной ветке.
Откат = просто не сливать ветку.

После слияния: `git revert` merge-коммита возвращает прежний сайт, Vercel пересоберёт его
автоматически за 1–2 минуты. Поэтому перед слиянием важно, чтобы старая версия оставалась
в истории целиком, а не была «переписана».

## 8. Что делать после миграции

По убыванию пользы:

1. **Собрать 2–3 реальных кейса с цифрами и согласием на публикацию.** Это по-прежнему
   единственное, что реально ограничивает убедительность сайта (см. HANDOFF.md).
2. Разобрать `global.css` на части и убрать inline-стили из разметки.
3. Настроить проверки: линтер, автотесты форм и маршрутов, CI.
4. Вернуться к CSP (заголовок безопасности, отложенный ранее) — после миграции inline-скрипт
   темы можно будет закрыть хэшем.

## 9. Оценка объёма

Точные сроки зависят от того, сколько правок вылезет при сверке скриншотов. Относительный вес:

- Фазы 0–1 (подготовка, каркас): небольшой объём
- Фаза 2 (оболочка, тема, Reveal): **самая сложная**, примерно четверть всей работы
- Фаза 3 (5 статичных страниц): самая большая по объёму, но механическая и предсказуемая
- Фаза 4 (формы): средний объём, требует аккуратной проверки
- Фазы 5–7 (SEO, сверка, уборка): небольшой объём, но фазу 6 нельзя торопить

Реалистично это несколько рабочих сессий, а не одна.
